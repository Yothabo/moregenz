# Unified Organisational Events and Notification Architecture

## 1. Purpose

This specification defines how organisational events are generated, processed, delivered and recorded across the parent company and all stores.

The platform MUST use one event and notification architecture for:
- Parent-company governance.
- Departments and teams.
- Store operations.
- Membership and position changes.
- Role and authority changes.
- Approval workflows.
- Shared services.
- Security and compliance events.

Notifications MUST communicate events. They MUST NOT independently grant permissions or execute unauthorised decisions.

## 2. Event Model

An event represents a recorded occurrence within the platform.

Each event MUST contain:
- Unique event ID.
- Event type.
- Event version.
- Occurrence timestamp.
- Initiating user ID, where available.
- Relevant organisational unit ID.
- Affected resource type and ID.
- Correlation ID.
- Event payload.
- Source system.

Events MUST use stable identifiers rather than display names.

Event payloads MUST contain only the information required by authorised consumers.

## 3. Event Categories

The platform MUST support these categories:

### 3.1 Identity and Membership
- Identity registered.
- Membership proposed.
- Membership activated.
- Membership suspended.
- Membership transferred.
- Membership ended.

### 3.2 Positions and Organisation
- Position created.
- Position occupied.
- Position vacated.
- Reporting relationship changed.
- Organisational unit created.
- Organisational unit restructured.
- Organisational unit suspended or closed.

### 3.3 Access and Authority
- Role assignment requested.
- Role assignment approved.
- Role assignment activated.
- Role assignment revoked.
- Delegation created or expired.
- Authority assignment changed.
- Access restriction triggered.

### 3.4 Decisions and Approvals
- Decision submitted.
- Approval requested.
- Decision approved.
- Decision rejected.
- Decision execution completed or failed.

### 3.5 Shared Services
- Service assigned to store.
- Service relationship activated.
- Service request created.
- Service request assigned.
- Service escalated.
- Service completed.
- Service relationship ended.

### 3.6 Security and Audit
- Privileged action performed.
- Unauthorised operation attempted.
- Emergency authority invoked.
- Audit integrity alert generated.

## 4. Event Generation

Events MUST be generated by authoritative backend operations.

The frontend MUST NOT be trusted to declare that a protected business event occurred.

Events MUST only be published after the originating operation has successfully committed.

Where an operation fails, the platform MUST NOT publish a successful completion event.

For database-backed operations, event publication SHOULD use a transactional outbox pattern to prevent committed changes from losing their corresponding events.

## 5. Event Processing

The event-processing system MUST:

1. Validate event structure and version.
2. Verify event origin.
3. Identify authorised consumers.
4. Process events idempotently.
5. Handle retries.
6. Record processing outcomes.
7. Prevent duplicate consequential actions.
8. Route failed processing for controlled recovery.

A failed notification MUST NOT reverse an already completed business decision.

Events that cannot be processed MUST enter a monitored failure or dead-letter workflow.

## 6. Notification Model

A notification is a user-facing communication generated from an event.

Each notification MUST identify:
- Notification ID.
- Recipient user ID.
- Source event ID.
- Notification category.
- Subject.
- Message.
- Relevant resource reference.
- Created timestamp.
- Delivery status.
- Read status, where applicable.

Notifications MUST be generated only for authorised recipients.

## 7. Recipient Resolution

Recipients MUST be determined using the event type, organisational scope, active memberships and applicable notification rules.

Examples:

- A store membership change may notify the affected person and authorised Store Owner.
- A department assignment may notify the responsible department leadership.
- A store service request may notify assigned service personnel and the authorised store contact.
- A financial approval request may notify only authorised approvers.
- A security incident may notify designated security personnel.

Being a department member MUST NOT automatically make someone a recipient of every departmental or store notification.

The platform MUST NOT expose another store's private operational information through notification content.

## 8. Delivery Channels

The platform MAY support:
- In-app notifications.
- Email.
- Approved messaging integrations.
- Mobile push notifications.

Each channel MUST follow the user's notification preferences where legally and operationally permitted.

Critical security, financial and governance notifications MUST follow mandatory delivery rules.

Channel failure MUST be recorded and MUST NOT be interpreted as approval or acknowledgement.

## 9. Notification Lifecycle

Notification statuses MUST support:
- Pending.
- Queued.
- Delivered.
- Failed.
- Read.
- Archived.

Delivery status and read status MUST remain separate.

Reading a notification MUST NOT automatically approve a decision, accept an appointment or complete a workflow.

## 10. Preferences and Suppression

Users MAY configure permitted notification preferences.

Users MUST NOT suppress mandatory:
- Security alerts.
- Access revocation notices where required.
- Formal approval requests.
- Compliance notifications.
- Critical operational incidents.

The platform MUST prevent duplicate notifications for the same event and recipient where the delivery policy requires deduplication.

## 11. Event and Notification Security

Event consumers MUST validate their authority before accessing referenced resources.

Event identifiers MUST NOT function as access credentials.

Notification links MUST require normal authentication and permission evaluation.

Sensitive information SHOULD be excluded from email and external messaging payloads. Recipients SHOULD be directed to authenticated platform views for protected details.

## 12. Audit and Observability

The platform MUST retain:
- Event publication records.
- Processing attempts.
- Consumer outcomes.
- Notification creation.
- Recipient resolution.
- Delivery attempts.
- Delivery failures.
- Read and acknowledgement records where supported.

Monitoring MUST identify:
- Stuck event processing.
- Repeated delivery failures.
- Duplicate processing.
- Unauthorised recipient resolution.
- Abnormal event volume.
- Dead-letter queue growth.

## 14. Acceptance Criteria

Implementation is compliant only when:

- Events originate from authoritative backend operations.
- Successful events are published only after successful commits.
- Event processing is retryable and idempotent.
- Notification recipients are resolved through authorised scope.
- Store information remains isolated.
- Delivery and read status are independent.
- Reading a notification cannot approve a decision.
- Notification links enforce normal access controls.
- Failed delivery is recorded and monitored.
- Event and notification activity is auditable.
